# Financial App

App financeiro do casal: API em Python (FastAPI) em `backend/`, app React + TypeScript em `web/`, infraestrutura AWS (CDK em TypeScript) em `infra/`. Spec e tickets em `.scratch/`.

## Pré-requisitos

Python 3.14 (o runtime da Lambda; `backend/.python-version`) com [uv](https://docs.astral.sh/uv/), Node 22, Postgres 16 (o mesmo do CI).

## Como rodar

```sh
eval "$(scripts/postgres-local.sh)"          # Postgres local sem Docker; exporta DATABASE_URL
(cd web && npm ci && node e2e/cognito-falso.ts)   # login de mentira na porta 9230 (veja Login)
(cd backend && uv sync && uv run python -m app.migrations)
(cd backend && JWT_EMISSOR=http://127.0.0.1:9230/sa-east-1_teste JWT_AUDIENCIA=cliente-de-teste \
  uv run uvicorn app.main:create_app --factory --port 8765)
(cd web && VITE_COGNITO_USER_POOL_ID=sa-east-1_teste VITE_COGNITO_CLIENTE_ID=cliente-de-teste \
  VITE_COGNITO_ENDPOINT=http://127.0.0.1:9230/ npm run dev)   # /api é repassado para a porta 8765
```

Com o Cognito falso, `flavio@teste.com` e `esposa@teste.com` entram com qualquer senha.

## Login

O app entra no Cognito por um formulário próprio (SRP, cliente público), e só o módulo `web/src/login/` conhece o Cognito. A sessão fica no IndexedDB do aparelho, nunca em cookie: refresh token de 10 anos e token de acesso de 15 minutos, renovado quando vence; sem internet, o app segue logado com o acesso vencido. A API só confere um JWT padrão, com emissor e audiência em `JWT_EMISSOR` e `JWT_AUDIENCIA` (chaves em `<emissor>/.well-known/jwks.json`), e tira o usuário do `sub`. Rota nova protegida recebe `usuario: UsuarioLogado` (`app/login.py`). O token não traz nome: `PESSOAS` (JSON `{"<sub>": "<nome>"}`) diz quem é quem para o app (`app/pessoas.py`, `GET /api/pessoas`); sem ela, o seletor de pessoa só tem "Conjunto" e os avisos dizem "a outra pessoa" (ticket 84).

O app lê o user pool no build: `VITE_COGNITO_USER_POOL_ID`, `VITE_COGNITO_CLIENTE_ID` e, só para o falso, `VITE_COGNITO_ENDPOINT`. O deploy preenche os dois primeiros com as saídas da pilha de dados.

Não há cadastro público: o dono cria os dois usuários, já com a senha definitiva, e desconecta todas as sessões de um celular perdido (o acesso já emitido vence em até 15 minutos):

```sh
scripts/usuarios-do-app.sh criar prod <email>
scripts/usuarios-do-app.sh desconectar prod <email>
scripts/usuarios-do-app.sh listar prod
```

## Como testar

```sh
(cd backend && uv run pytest)                # rotas em processo contra o Postgres de DATABASE_URL
(cd web && npm run typecheck && npx playwright test)   # sobe Cognito falso, API e app; o teste desliga a rede
```

O CI (`.github/workflows/ci.yml`) roda lint, testes, o contrato e o build com um Postgres em container.

## Lançamentos

`backend/app/lancamentos.py` tem contas, categorias e lançamentos simples (valor em centavos inteiros, uma ou mais categorias, id UUID gerado no aparelho). No app, `#/novo` lança (o atalho "Novo lançamento" do manifesto abre direto nele): valor pelo teclado próprio, fileiras de conta ou cartão e categorias, "Repetir último" enquanto o lançamento está vazio e a folha de detalhes (descrição, tags, pessoa, data hoje/ontem/outra, situação e, no cartão, a fatura), resumida numa linha embaixo do valor. A tag nova vai pelo nome e nasce no servidor com o lançamento. `#/historico` lista, edita e exclui, e `#/contas-e-categorias` cria conta e cria, renomeia e arquiva categoria.

Sugestão pela descrição (tickets 22 e 63): `GET /api/sugestoes` (`backend/app/sugestao.py`) devolve o índice da fonte "histórico" e a hora do servidor em que foi montado (`gerado_em`). Cada sugestão traz tipo, conta, categorias, tags e pessoa de um lançamento não excluído, agrupada pela descrição normalizada (`chave`: sem acento, sem maiúscula, sem `(n/total)`), com no máximo `sugestao.maximoDeSugestoes` sugestões diferentes por descrição, da mais recente à mais antiga. A recência (`em`) é a criação ou a última mudança na descrição, no tipo, na conta, nas categorias, nas tags ou na pessoa: corrigir as categorias põe a sugestão primeiro, e mudar o valor não. O previsto de uma recorrência conta pela hora da regra, então a ocorrência que a tarefa diária gera depois não passa na frente de uma correção. Categoria e tag arquivadas saem da sugestão. O casamento roda no aparelho (`web/src/dados/sugestao.ts`): igual, depois "começa com", depois palavra que começa com o digitado, a partir de `sugestao.letrasMinimas` letras. O índice é guardado como as outras leituras e buscado de novo logo depois de cada envio da fila (ao abrir, ao voltar ao app e quando a rede volta). O `useSugestao` põe por cima dele os lançamentos que ele ainda não tem (os não enviados e os que mudaram depois de `gerado_em`), então o que se acabou de lançar ou corrigir, mesmo sem internet, já é a sugestão mais recente. Escolher preenche conta, categorias, tags e pessoa (e o tipo que as categorias têm) e mantém o valor, a data e a descrição.

Sem internet ([ADR 0011](docs/adr/0011-sem-internet-so-lancamentos-e-conflito-decidido-a-mao.md)): as telas leem e escrevem só por `web/src/dados/`, que guarda no IndexedDB do aparelho a última resposta de cada leitura ("atualizado às 14:32") e a fila dos lançamentos não enviados, no máximo uma mudança por lançamento. A fila sobe por `POST /api/lancamentos/lote`: as ações na ordem, cada uma na sua transação, com um resultado por ação (`aceita`, `recusada` com o motivo, `conflito` com o lançamento do servidor e os `campos` em conflito, `descartada` com a `exclusao` quando o outro lado excluiu). O lote fica em `backend/app/lote.py` e aceita também `confirmar` (as regras da rota de confirmar, com a `versao` e só os ajustes) e `criar_parcelamento`, que grava o parcelamento como um pedido só e gera as parcelas no servidor. Ela sobe ao abrir o app, ao voltar para ele, quando a rede volta e pelo "Enviar agora" da Hoje; no Android, também pelo `sync` do service worker, que o build monta com `web/src/dados/segundoPlano.ts` empacotado (`vite.config.ts`). Sair da conta apaga a fila e as respostas guardadas.

Conflito ([ADR 0011](docs/adr/0011-sem-internet-so-lancamentos-e-conflito-decidido-a-mao.md)): cada lançamento traz `versao`, que sobe a cada mudança aceita, e o servidor guarda em `lancamento_campos` a versão, quem e quando de cada campo. `PATCH /api/lancamentos/{id}` leva só os campos mudados e a `versao` sobre a qual a mudança foi feita: campos diferentes se mesclam, mudança igual à gravada passa, e campo que o outro lado mudou depois para outro valor dá 409 com o lançamento do servidor e os campos em conflito (quem, quando, `por_voce`, `origem` da regra). Excluir só marca `excluido_em`; a edição de algo excluído dá 410 com quem excluiu, e `DELETE /api/lancamentos/{id}?versao=N` dá 409 se o outro lado mudou depois. No app, a fila guarda a versão que a tela mostrava (`base`) e sobe só o que mudou desde ela; o conflito fica marcado "⚠ conflito" com a versão do servidor na tela até a decisão em `#/conflito/<id>`, e a exclusão que venceu mostra o aviso com "Lançar de novo".

Hoje (ticket 53): `GET /api/hoje` (`backend/app/hoje.py`) é a leitura única da aba, já somada no servidor: `ainda_da_para_gastar_centavos` e `planejado_centavos` do planejamento do mês de hoje (sem recalcular), `a_escolher` com os `lancamentos_a_escolher`, `contas_da_semana` (os atrasados trazem `atrasado`), `faturas_que_vencem` (fechadas, com saldo a pagar, que vencem em até `contasDaSemanaDias` dias ou já venceram) e `itens_em_destaque` (itens do planejamento a partir de `itensEmDestaqueNaHojePercentual`, do mais cheio ao menos). No app, `useHoje` (`web/src/dados/`) guarda a última resposta e a tela (`web/src/hoje/TelaHoje.tsx`) mostra "atualizado às" sem internet; escolher o item de um "a escolher" vai pela fila, e os avisos de não enviados e de conflito são o `AvisoDaFila`. O bloco "Contas da semana" recebe os previstos da leitura da Hoje; `GET /api/contas-da-semana` segue existindo.

Previsto e realizado ([ADR 0004](docs/adr/0004-previsto-e-situacao-do-lancamento.md)): sem `situacao`, data futura nasce prevista; a tela de lançamento troca à mão na folha de detalhes. Cada lançamento traz `atrasado` (previsto com data antes de hoje em São Paulo). `POST /api/lancamentos/{id}/confirmar` vira o previsto em realizado, com ajuste opcional de valor, data e conta; confirmar de novo sem ajuste diferente devolve o gravado, e com ajuste diferente dá 409 com quem confirmou, que o app leva à tela de conflito. `GET /api/contas-da-semana` lista os previstos atrasados e os dos próximos `contasDaSemanaDias` dias, em ordem de data, e a aba Hoje mostra o bloco "Contas da semana" com "Confirmar" e "Ajustar". A confirmação entra na fila como as outras mudanças (ticket 83), e o bloco mostra as contas da semana da leitura da Hoje com a fila por cima: o previsto criado ou mudado no aparelho entra ou sai pela mesma janela de `contasDaSemanaDias`, e o confirmado sai, com o Histórico o mostrando realizado ⏳. Confirmar o que ainda não subiu muda o pedido que já está lá, e editá-lo depois sem mudar a data não desfaz a confirmação. A confirmação em conflito vai para `#/conflito/<id>`; enquanto espera, o bloco mostra "Decidir", e a recusada fica no bloco com o motivo. Os testes de API fixam o dia trocando `app.lancamentos.hoje`.

Recorrência (ADR 0004): `backend/app/recorrencias.py`. `POST /api/recorrencias` grava a regra (a cada `a_cada` semanas ou meses desde `inicio`, sem fim, até `ate` ou por `vezes`; `tipo_do_valor` `fixo` ou `estimado`, e só o fixo pode ser `automatico`) e gera os previstos até o horizonte (`horizonteDaRecorrenciaMeses`), em lotes de uma transação cada; o mesmo id reenviado devolve a gravada com 200. Cada previsto traz `recorrencia_id` e `ocorrencia`, e o id dele vem da regra e do número da ocorrência, então gerar de novo não duplica e o previsto excluído não volta. Os previstos herdam valor, descrição, conta, categorias, tags e pessoa; o automático com data até hoje já nasce realizado, fica fora das contas da semana e nunca aparece `atrasado`. A tarefa diária (`app.tarefa_diaria.handler`, às 00:07 de São Paulo) estende o horizonte e realiza os automáticos do dia, com a `origem` "a recorrência <descrição>" na versão do campo. Só a API existe: a tela e o pedido na fila são do ticket 86.

Parcelamento (ADR 0004): `backend/app/parcelamentos.py`. `POST /api/parcelamentos` grava a compra ou a dívida em `parcelas` (2 a `maximoDeParcelas`, 420) com `valor_total_centavos` ou `valor_da_parcela_centavos` (um dos dois; os centavos que sobram da divisão do total vão na 1ª) e gera todas as parcelas, em lotes de uma transação cada; o mesmo id reenviado devolve o gravado com 200. Cada parcela é um lançamento com `parcelamento_id`, `parcela` e `parcelas` (3 de 10), id vindo do parcelamento e do número, e herda descrição, conta ou cartão, categorias, tags e pessoa. No cartão, todas têm a data da compra e a parcela n cai n - 1 faturas depois da fatura da compra (a redistribuição pelas datas do cartão e a edição da data mantêm a distância); o parcelamento no cartão é sempre `automatico`, e a parcela vira realizada quando a fatura de antes fecha (a 1ª, na data da compra). Fora do cartão (o boleto), a parcela n vence n - 1 meses depois de `data` e pede confirmação, salvo com `automatico`. A tarefa diária completa a geração que parou no meio e realiza as parcelas automáticas, com a `origem` "o parcelamento <descrição>"; a realização dos automáticos das duas regras fica em `app/automaticos.py`. A planilha da exportação escreve a parcela como o Mobills: "Geladeira (3/10)". A tela e o pedido na fila são do ticket 98.

Correção do parcelamento (ticket 47): `PATCH /api/parcelamentos/{id}` muda descrição, categorias, tags, pessoa e item (vale para todas as parcelas, inclusive as realizadas, com a `origem` "o parcelamento <descrição>" no conflito) e, além disso, `valor_total_centavos` ou `valor_da_parcela_centavos`, `parcelas` e `data`, que refazem as parcelas em lotes de uma transação; só o número de parcelas mantém o total. A parcela que uma pessoa editou à mão (valor, data, conta ou fatura; `alterada_a_mao` no lançamento) fica como está, e tirá-la ao encolher o parcelamento é 422. Se uma realizada vai mudar ou sair, a resposta é 409 com `parcelas` (antes e depois) e nada é gravado até o pedido vir com `confirmar_realizadas`. A parcela excluída uma a uma não volta; as que saíram ao encolher voltam se o parcelamento crescer. A parcela automática que a data nova já alcançou se realiza na hora. `DELETE /api/parcelamentos/{id}` (idempotente) exclui o parcelamento e todas as parcelas, as realizadas também. A tela é do ticket 98.

`backend/app/transferencias.py` registra a transferência entre duas contas ([ADR 0014](docs/adr/0014-transferencia-em-tabela-propria.md)). A conta guarda o saldo de abertura (valor e data) e pode ser arquivada (`PUT /api/contas/{id}`); `GET /api/contas` devolve `saldo_centavos` (abertura mais os realizados depois da data) e esconde as arquivadas, salvo com `?arquivadas=true`. No app, "Transferência" no seletor de tipo do `#/novo` abre a tela de transferência (de, para, categoria opcional), que grava direto na API e precisa de internet.

Cartões e faturas ([ADR 0003](docs/adr/0003-compra-no-cartao-conta-no-mes-da-fatura.md), [ADR 0015](docs/adr/0015-compra-no-cartao-guarda-o-cartao-e-o-mes-no-lancamento.md)): `backend/app/cartoes.py` tem o cadastro (`/api/cartoes`: dias de fechamento e vencimento padrão, limite opcional, `mes_anterior_ao_fechamento`, adicional com `titular_id` e arquivar pelo `PUT`) e as faturas (`GET /api/cartoes/{id}/faturas`, `PATCH /api/cartoes/{id}/faturas/{mes}` para acertar fechamento e vencimento); `backend/app/faturas.py` escolhe a fatura. A compra no cartão é um lançamento com o cartão em `conta_id`: o servidor escolhe a primeira fatura que fecha depois da data da compra (no dia do fechamento já é a seguinte), cria a fatura se ela ainda não existe e devolve `fatura_mes`. Mandar `fatura_mes` é a troca de fatura à mão, que fica mesmo se a data ou o dia padrão mudarem. Todo lançamento traz `mes`, o mês em que conta (o da fatura no cartão, o da data no resto), gravado e indexado. Mudar o dia padrão do cartão ou as datas de uma fatura redistribui as compras das faturas abertas e futuras, como mudança do app (sobe a versão, com a `origem` "datas do cartão ..."); fatura fechada não muda. O adicional não tem fatura própria: as compras dele caem na do titular. A aba Cartões (`#/cartoes`, `web/src/cartoes/`) traz uma linha por cartão titular com a fatura anterior, a atual (a primeira aberta) e a próxima, a situação e o total; tocar numa fatura abre `#/cartoes/<cartão>/<mês>`, com as compras agrupadas por dia (as do adicional incluídas) e filtro por categoria e tag. Sem internet, mostra a última resposta guardada. As telas de cadastro são do ticket 88.

Pagamento de fatura (ticket 38): é `POST /api/transferencias` com a conta de origem, o cartão em `conta_destino_id` e o `fatura_mes` que ele quita (obrigatório nesse caso, sem categoria; pagar o adicional quita a fatura do titular). O saldo da conta cai na data do pagamento realizado, antes ou depois do vencimento, e nenhum `mes` de compra muda. As faturas passam a trazer `total_centavos`, `saldo_anterior_centavos` (o que sobrou da fatura anterior fechada, que não é compra e não conta de novo), `pago_centavos`, `a_pagar_centavos` e a situação `paga`. Juros, IOF e multa do rotativo são compras comuns na fatura seguinte.

Estorno, ajuste de fatura e compra cancelada ([ADR 0008](docs/adr/0008-ajuste-de-fatura-fica-na-fatura.md), [ADR 0016](docs/adr/0016-estorno-e-lancamento-que-diminui-ligado-a-compra.md)): cancelar uma compra é excluí-la (`DELETE /api/lancamentos/{id}`), e ela some da fatura, do mês, das categorias, das tags e do planejamento. O estorno é um lançamento criado com `estorno_de` (o id da compra original): despesa num cartão, com as mesmas categorias e tags da compra e valor que, somado aos outros estornos dela, não passa do dele; ele cai na fatura pela data, como qualquer compra, e diminui a fatura, o mês, a categoria, a tag e o item. O ajuste de fatura é `ajuste_centavos` no `PATCH /api/cartoes/{id}/faturas/{mes}` (positivo ou negativo; `0` desfaz); a fatura devolve `compras_centavos` (compras menos estornos), `ajuste_centavos` e `total_centavos`. `GET /api/meses/{mes}/totais` (`app/meses.py`) devolve as despesas do mês (compras menos estornos, mais os ajustes) e os totais por categoria e por tag, que não levam o ajuste; o planejamento devolve `ajustes_de_fatura_centavos` e desconta os ajustes do mês de `ainda_da_para_gastar_centavos`, mas não dos itens.

## Planejamento

`backend/app/planejamento.py` guarda os itens do planejamento de cada mês: uma categoria (de despesa, receita ou transferência) e um valor, no máximo um item por categoria e mês. `POST /api/planejamento/{mes}/itens` cria (reenviar o mesmo id devolve o gravado), `PATCH` e `DELETE /api/planejamento/itens/{id}` mudam o valor e excluem, e `GET /api/planejamento/{mes}` (`AAAA-MM`) devolve o mês numa chamada só, já somado: por item o planejado, o realizado, o previsto (inclusive o atrasado), a porcentagem `(realizado + previsto) / planejado` e o "ainda dá para gastar" (planejado menos realizado e previsto, negativo se estoura); o do mês soma o que falta em cada item, sem abater item estourado. Cada lançamento conta em no máximo um item (`app/item_em_que_conta.py`): no da escolha do casal (`item_categoria_id` no lançamento, uma das categorias dele, que vale em qualquer mês em que ela tem item), ou sozinho quando só uma das categorias tem item no mês. Com duas ou mais e sem escolha, ele entra em `a_escolher` da leitura do mês e fica no item em que já contava quando a ambiguidade surgiu (item criado depois, categorias editadas, outro mês). A recorrência e o parcelamento guardam a escolha (`item_categoria_id`) e seus lançamentos nascem com ela; o estorno nasce com o item da compra. Juntar categorias soma os itens do mesmo mês no destino, e excluir categoria recusa se há item. Só a API existe: as telas são dos tickets 52 e 54.

## Importador do Mobills

`backend/app/mobills/` lê os exports do Mobills e cruza cada linha de fatura com o seu par no geral ([ADR 0007](docs/adr/0007-historico-do-mobills-cruzado-e-sem-saldo.md), `## Answer` do ticket 18). O dono roda localmente, com os exports fora do repositório (`data/` está no `.gitignore`):

```sh
(cd backend && uv run python -m app.mobills <pasta do geral> <pasta das faturas> <planilha.xlsx>)
```

A pasta do geral tem os XLSX de "todas as transações"; a das faturas, uma subpasta por cartão com os arquivos `<cartão>_-_<AAAAMM>.xlsx`. Cada rodada lê a planilha de revisão da anterior, se existir, e a reescreve mantendo o que o dono editou: as abas Conta e Cartões (o cadastro, com cada pasta ligada a um cartão e os inativos arquivados), De-para (papel e nome no app de cada categoria e tag), Pares prováveis (`juntar` ou `separar`), Parcelamentos sem cartão (o cartão escolhido) e a coluna Mobills das abas Conferência e Faturas, que dá a diferença na rodada seguinte. Grupos ambíguos, Categoria diferente e Parcelas quebradas só informam. A saída da linha de comando mostra a taxa de casamento e o que ainda impede gravar (sai com código 2 enquanto houver impedimento); um export ou uma planilha que não dá para ler sai com código 1 e a mensagem do arquivo. A Conferência vai até o último mês com lançamento pago (a virada). Por enquanto o resultado fica em memória (`importar` devolve a `Importacao`): gravar no banco e refazer apagando só o importado dependem dos cartões e faturas (ticket 37). `openpyxl` fica no grupo `dev`, fora do pacote da Lambda.

## Contrato (OpenAPI e tipos)

A FastAPI gera o OpenAPI; `openapi.json` fica versionado e o app gera os tipos dele. Depois de mudar uma rota ou um modelo:

```sh
(cd backend && uv run python gerar_openapi.py)
(cd web && npm run gerar-tipos)
```

O CI falha se `openapi.json` ou `web/src/api/schema.d.ts` estiverem desatualizados.

## Migrations

Arquivos `backend/migrations/NNNN_nome.sql`, um DDL por arquivo, no subconjunto do Aurora DSQL (sem triggers nem PL/pgSQL). `aplicar_migrations` aplica em ordem as que faltam e as registra em `controle_de_migrations`. Preencher uma coluna nova é a exceção ao DDL: um `UPDATE` de no máximo 3.000 linhas (o limite da transação no DSQL), como a `0034`. Índice se escreve `CREATE INDEX ASYNC`, o único que o DSQL aceita; fora dele (local e CI), o `ASYNC` sai e o índice nasce na hora.

## Configuração

Os valores iniciais da spec (3 sugeridos, 5 usos, 24 h, 80% etc.) ficam só em `config/valores-iniciais.json`, lido pela API (`app.config.valores_iniciais`) e importável pelo app.

## Deploy

O workflow `.github/workflows/deploy.yml` publica pelo GitHub Actions com OIDC (role `financial-app-deploy`, sem chave de longa duração): o merge na `main` publica em `prod`; push em outra branch, ou o botão "Run workflow", publica em `dev`. Conta e região ficam só em `config/aws.json`.

Cada ambiente tem duas pilhas: `financial-<ambiente>-dados` (cluster Aurora DSQL, user pool do Cognito e o bucket do backup) e `financial-<ambiente>-app` (Lambda arm64 com a API, HTTP API com limite de 10 por segundo e rajada de 20, PWA num S3 privado, o CloudFront, que leva `/api/*` à HTTP API sem cache, a Lambda do backup diário e a da tarefa diária das recorrências e dos parcelamentos, com um alarme por e-mail se ela falhar). O deploy segue esta ordem: pilha de dados, migrations e papéis (`api` e `backup`) no DSQL, build da PWA com o user pool do ambiente, pilha do app (no `dev`, com um backup de verdade, veja abaixo) e o teste de fumaça (`scripts/conferir-deploy.sh <endereço>`), que exige `/api/saude` ok com todas as migrations e `/api/eu` recusado sem token. As políticas das pilhas (`infra/politicas/`) proíbem substituir ou remover a distribuição, o banco, o user pool e o bucket do backup, porque a PWA instalada fica presa ao endereço do CloudFront e o bucket guarda os backups travados.

Backup diário (ADR 0012): às 03:07 de São Paulo, o EventBridge Scheduler chama a Lambda `app.backup_diario.handler`, que entra no DSQL com o papel `backup` (só `SELECT`), gera o zip numa transação só, confere as contagens do zip contra o banco e grava `diario/AAAA-MM-DD.zip` no bucket `BucketDoBackup` (saída da pilha de dados). O bucket tem versões e Object Lock em compliance por 90 dias em `prod` (1 dia no `dev`), e o ciclo de vida apaga as versões depois do prazo. Um e-mail chega pelo tópico `Avisos` se a Lambda falhar ou se passarem 26 horas sem backup concluído (métrica `FinancialApp/BackupsConcluidos`). No `dev`, cada deploy com código novo também roda um backup (Trigger do CDK) e falha se ele falhar. Para baixar um backup: `aws s3 cp s3://<bucket>/diario/AAAA-MM-DD.zip .`; as versões de um mesmo dia aparecem em `aws s3api list-object-versions --bucket <bucket> --prefix diario/`. O bucket fica na conta mesmo se a pilha for apagada: com objetos travados o CloudFormation não o apaga, e ele se esvazia pelo ciclo de vida.

Exportar tudo (ADR 0012): a tela Configurações do app (só com internet) chama `POST /api/exportacoes` com `{"formato": "backup"}` (zip de CSVs, o mesmo gerador do backup diário) ou `{"formato": "planilha"}` (CSV de lançamentos com `;`, vírgula decimal e UTF-8 com BOM). A API grava o arquivo em `exportacoes/` no bucket `BucketDeExportacoes` (variável `EXPORTACOES_BUCKET`), sem Object Lock e com expiração de 7 dias, devolve uma URL assinada de 5 minutos e registra quem pediu na tabela `exportacoes`. A planilha (`ler_lancamentos`) traz todo o histórico de lançamentos e transferências, sem os excluídos, com os nomes no lugar dos ids: conta ou cartão, fatura (`AAAA-MM`, só no cartão), categorias e tags separadas por ` | `, pessoa e autoria pelo nome de `PESSOAS`; a transferência é uma linha com "origem → destino".

Restauração (ADR 0012): `scripts/restaurar-backup.sh <prod|dev> <arquivo.zip>` grava um backup no banco do ambiente com a credencial do dono (`app.restauracao`, entra no DSQL como `admin`). Ela só roda num banco vazio e com as mesmas tabelas do backup (as migrations aplicadas), recusa versão de formato desconhecida e converte as antigas (`CONVERSORES` em `app/backup.py`). Grava em lotes de 1.000 linhas, porque o DSQL limita as linhas por transação; se um lote falhar ou as contagens e somas do banco não baterem com o manifesto, apaga o que gravou e o banco volta a ficar vazio. No fim, exporta de novo e exige o mesmo zip. O ensaio no `dev` com o backup de `prod`, antes da virada e a cada mudança no formato, leva `--esvaziar`, que apaga os dados do `dev` antes (recusado em `prod`). Uma migration que muda as tabelas faz o teste `test_formato_do_backup.py` falhar até `VERSAO_FORMATO` subir, com o conversor da versão anterior e o esquema novo em `backend/tests/esquemas_do_formato.json`.

Alarmes de custo e de erros (e-mail do dono em `config/aws.json`, `emailDoDono`): a pilha `financial-orcamento` (da conta, não de um ambiente) cria o orçamento mensal sem créditos com alertas em US$ 1 (real), US$ 5 (previsão) e US$ 5 (real); ela é publicada à mão, como a `financial-github` (`cd infra && npx cdk deploy financial-orcamento`). Cada pilha do app tem um alarme de mais de 5 respostas 5xx por dia na HTTP API, os dois do backup e o da tarefa diária que falhou, avisando pelo mesmo tópico SNS e e-mail. Depois do primeiro deploy, o dono confirma a inscrição do SNS que chega por e-mail. `npm test` em `infra/` confere o orçamento, o alarme de 5xx e o da tarefa diária.

Para conferir as pilhas localmente:

```sh
scripts/empacotar-lambda.sh                  # pacote da Lambda em build/lambda (arm64, python3.14)
(cd web && npm run build)
(cd infra && npm ci && npm run typecheck && npm run synth)
```
